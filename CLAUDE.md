# Attnd iOS

SwiftUI app that lets attendees discover and follow live events. Consumes the Attnd REST API v2 served by **[attnd-web](https://github.com/apbeers/Attnd-Web)** (contract: [`API_V2.md`](https://github.com/apbeers/Attnd-Web/blob/develop/API_V2.md) in attnd-web).


## Branching (initial development)

- `main` = production (default branch), `develop` = dev/beta. Pushing to `develop` deploys to the dev server / TestFlight / Play internal testing; pushing to `main` deploys to production.
- **While there are no real users yet, commit and push straight to `develop`** — no feature branches or PRs needed. Merge `develop` → `main` to release. Revisit this once the apps have users.


## API changes start in attnd-web

attnd-web is the coordinating repo. The API contract ([`API_V2.md`](https://github.com/apbeers/Attnd-Web/blob/develop/API_V2.md)) and the cross-repo tracker ([`API_CHANGES.md`](https://github.com/apbeers/Attnd-Web/blob/develop/API_CHANGES.md)) live there only; this repo has no copy.
- Don't build against API behaviour that isn't in `API_V2.md`. If a feature needs an API change, add it in attnd-web first (tracker entry, server, contract), then implement the app part here.
- Implement what the tracker entry's app section says. Put its ID in the commit message (e.g. `API-003: …`), then tick this app's column in attnd-web's `API_CHANGES.md`.
- Keep decoding lenient: ignore unknown keys and default missing ones, so additive server changes never break shipped builds.

## Dependency Policy

**Apple frameworks only; no third-party packages.** No SPM, CocoaPods or Carthage dependencies, no Firebase. Push uses APNs directly via `UIApplication` / `UserNotifications`.

## App Flow

```
Launch
├── registerForRemoteNotifications() (full app, every launch, opt-in or not)
├── POST devices/ (registration, push token if any — never "", subscribed = alert opt-in)
├── Saved copy on disk for the saved event code? → shown at once (works offline), then
│   POST join/ + GET bundle/ in the background (join retried after a later successful refresh)
├── Else saved event code? → GET events/lookup/?q=<code> → join silently
│   └── 404 → code forgotten; offline / none saved → LaunchScreen
│
LaunchScreen
├── GET events/nearby/?lat=&lng=
├── QR scan / search → GET events/lookup/?q=<code or exact name>
│
Join event
├── POST events/<id>/join/ {device_id, platform: "ios", push_token, app_version}
└── GET events/<id>/bundle/ (If-None-Match, X-Device-Id)
│
ContentView (tabs and default tab from bundle.display, at most 5; search button + Options item open sheets)
├── Map / Locations / Schedule / Flyer / Updates; sheets: Search (local, all content), Options
├── Bundle refetched on: foreground, pull-to-refresh, a content_updated push with a newer
│   content_version (random 0–10 s delay; foreground or background), notification pushes,
│   and a fallback poll while active: 60 s without a push token (always in the App Clip),
│   5 min with one, 15 s after a failed refresh (304 when unchanged)
├── Every applied bundle → saved to disk + images prefetched + search index rebuilt +
│   Spotlight entities re-indexed (app only); a 404 → event forgotten
├── POST events/<id>/usage/ (anonymous counts): every ~60 s with pending data, on background
└── Live Activity / reminders / venue monitor follow every applied bundle, heart and scene
    activation (LiveFollowController; full app only); its push token → POST devices/
    live_activity_token (null when it ends)
│
Leave event (or switch)
├── Pending usage counts flushed first
├── Saved copy, cached images and Spotlight entities deleted
└── POST events/<id>/leave/ {device_id}
```

## Usage reporting (API-005)

- Anonymous counts only: `POST events/<id>/usage/` with `{"platform": "ios", "events": [{name, detail?, count, at}]}`. **Never** a device ID, any identifier, or search text.
- Call sites use `appState.track(.metric, detail:)` / `track(.metric, id:)`; it is a no-op outside an event. `UsageReporter` (main actor, in `AppState.swift`) aggregates in a pure `UsageAggregator` (`Models.swift`) keyed by (event, name, detail, UTC 5-minute bucket; `at` = start of the bucket, e.g. `2026-11-14T16:05:00Z`) and flushes at most every 60 s, when the scene goes to the background (`AppRootView`) and before leaving or switching events. A failed batch is retried once on the next flush, then dropped; errors are never shown. Max 200 entries per request.
- Hearts (API-009): `location_heart` / `location_unheart` (detail = location id) and `schedule_item_heart` / `schedule_item_unheart` (detail = item id), counted by `AppState.setHeart` (rows, details, map card, search, peeks, Siri) only when the state actually changes. Older servers drop unknown names harmlessly.
- Instrumented: `app_open` (silent rejoin at launch; scene becomes active in `ContentView`), `tab_view` (`selectedTab` didSet; the opening tab when the first bundle is applied; `options` when the Options sheet opens, `presentedSheet` didSet), `location_view` / `schedule_item_view` (`.task(id:)` on `LocationDetailView` / `ScheduleItemDetailView`, so every route counts), `notification_open` (`handlePush(opened: true)`), `search` (`SearchUsageCounting`, used by `SearchableIf` and the search sheet: on submit, or once a non-empty query settles for 1.5 s; no detail, never the text), no `tab_view` for the search sheet (`EventSheet.search.usageDetail` is nil: the server accepts only the event tabs and `options`), `refresh` (`AppState.pullToRefresh()` from every `.refreshable` in an event).

## Logging & diagnostics (API-013, API-014)

Shared spec with Android and attnd-web; the record format and **every event name** are in attnd-web `LOG_EVENTS.md` (only names listed there may be logged; add a row there first), the endpoints in `API_V2.md` → Diagnostics. Tests: `AttndTests/LoggingTests.swift` (redaction, record keys, gzip/CRC-32, debug codes, perf buckets, upload body, `Retry-After`, ring buffer).
- **Facade** `AppLog.debug/info/…(.cat, "event.name", "msg", [fields])`: message and fields are autoclosures, built only when the level is captured (`LogCore.isEnabled`, one `NSLock`); the record (seq, ts with ms, `mono_ms` from `ContinuousClock` since launch, app/build/os/model, `state` fg/bg from the scene phase, `net` from `NWPathMonitor`, `event_id`, `diag`) is encoded and written on one serial utility queue. Each record also goes to `os.Logger` (subsystem `com.arcu.Attnd`, category = `cat`; event name public, text public only in Debug/Dev builds). `AppLog.caught(error, .cat, "where")` logs `error.caught` (domain, code, type, where); use it in every `catch` that would otherwise be silent.
- **Redaction** (`LogRedaction`): never search/Ask/plan text in production (`textFields` → `query_len`; Debug/Dev builds add `query`), never tokens, keys, push / Live Activity tokens, JWTs, emails, the device id or support code (`scrub` runs on every message and string field: URL queries, bearer tokens, JWTs, emails, UUIDs, long hex, `key=value` secrets); URLs as path templates (`events/{id}/bundle/`); coordinates rounded to 0.01°. The debug code is never in support info or `devices/`.
- **Levels** (`LogPolicy`): Debug and Dev builds `debug` (disk); production captures `info` into a 5-minute in-memory pre-roll and keeps `warning`+ on disk, uploads nothing.
- **Ring buffer** (`LogStore`): `Application Support/attnd-logs/current.jsonl` + `previous.jsonl` (1 MB each, rotated, excluded from backup); `seq` continues across launches (read from the file's tail).
- **Uploads** (`LogUploader`): Dev builds always (`reason: "dev"`, one code per install in `log.devCode`), production only in debug mode (`reason: "debug_mode"`); never in screenshot mode; the App Clip only as a Dev build. `POST /api/v2/diagnostics/logs/`, gzip (`Content-Encoding: gzip`), ≤ 500 entries / 256 KB of JSON per request (a 413 halves the batch), every ~10 s (debug mode) / ~30 s or 200 records (Dev), and when the scene goes to the background; a `429`'s `Retry-After` is honoured (an older server's 404 waits an hour); failures back off and keep the lines. The cursor (last uploaded `seq`) is `log.upload.cursor`. Uploads aren't logged as requests (only `logging.upload`).
- **Request headers** (`APIClient.perform`): every call (retries too) a new `X-Request-Id` (32 hex), logged as `req_id` in `net.request.started/finished/failed`; `X-Diag-Session: D-XXXXX` while a session uploads. Failures and HTTP ≥ 400 (except the first 401) count `perf_api_error`.
- **Debug mode** (Options → About & Support → "Turn On Debug Logging for 10 Minutes", production, never remote): a new `D-XXXXX` (Crockford base32, `DebugCode`), Copy, countdown, Turn Off; level `debug` + upload for 10 min, starting with the previous 5 minutes (pre-roll flushed to disk); code/expiry/start in `log.debugMode.*`, so it survives restarts and turns itself off (`logging.debug_mode`). Viewer: "Logs" in Debug/Dev builds, "Recent Logs" in production (disk + pre-roll); not in screenshot mode.
- **Signposts** (`AppSignpost`, Instruments category `perf`, also `perf.signpost`): `launch`, `bundle_fetch` (request → decoded), `planner` (the Planner run), `map_first_render` (Map tab appears → first `onMapCameraChange(.onEnd)`).
- **Perf counts (API-014)** through `PerfMetrics` → `UsageReporter` (the joined event's batch, or the next one; ≤ 50 waiting): `perf_bundle_fetch` / `perf_bundle_304`, `perf_api_error`, `perf_push_refresh_delay` (`content_updated` → applied), `perf_live_start_fail` (disabled/limit/error), `perf_planner_ms`, `perf_map_first_render`; `perf_launch_cold` / `perf_launch_warm` from MetricKit's daily histograms in the app (time to first draw / resume time, one count per bucket), measured by `LaunchTiming` in the App Clip. Labels exactly as the server's (`PerfBucket`, e.g. `<0.5s`, `>=4s`).
- **MetricKit** (`MetricKitReporter`, app only, not in screenshot mode): crash, hang, CPU, disk-write and launch diagnostics → `POST diagnostics/reports/` (`kind`, `occurred_at`, per-report build/os/model, `summary`, `reason`, `exception`, `payload` = `jsonRepresentation()`, `diag` while a session uploads; no identifier), stored in `attnd-logs/reports/` until sent (≤ 20, ≤ 7 days). Daily metric payloads are never uploaded. Symbolication: the admin panel dispatches `symbolicate.yml` with the build's `dsyms-<build>` artifact.
- **App Privacy** (App Store Connect): Diagnostics → Crash data, Performance data, Other diagnostic data: not linked to identity, not used for tracking.

## API v2 Notes

- Base URL `https://attnd.app/api/v2/`. Attestation endpoints remain at `/api/v1/attest/`.
- Models must ignore unknown keys and default missing ones (see attnd-web `API_V2.md` → Display defaults). Decoding helpers in `Models.swift` (`lenient`, `lossyArray`) enforce this; add new fields the same way.
- Coordinates may be `null`; `0,0` is treated as unknown. Never drop a pin without a valid coordinate.
- Schedule items may have no location — shown under "General".
- All times are displayed in the **event's** `timezone` (`EventTimeFormat`), never the device's.
- `is_demo` / `status == "archived"` → a small floating capsule badge ("Demo event" / "Event ended") at the top of each tab's content (`eventStatusBanners()` in `ContentView.swift`): an overlay, so content scrolls under it; touches pass through; kept clear of reserved regions. While the last refresh failed, a second capsule says "Offline · Updated 3:41 PM" (or "Can't update · …"; `LastUpdatedText`, last successful refresh in the **device's** time zone). Map chips move down by `EventStatusBadgeKind.reservedTopHeight(_:)` (one `reservedHeight` per badge).
- Tags (API-010): `Location.tags` and `ScheduleItem.tags` arrive lower case (`"live music"`); filter and search on them as sent, show them through `TagText` ("Live music · Free"). Location tags are searched like item tags (weight 2).
- `AppNotification.priority` (API-011): `urgent` (anything else or missing = `normal`) is shown with a red "Urgent" label and a red-tinted row in Updates, and for 12 h (until dismissed) as the prominent red `UrgentUpdateBanner` above the other tabs and in the Live Activity's urgent block.
- `display.accent_color` (or the event's) tints the app. Otherwise the tint is the asset `AccentColor` (brand purple `#431F86`, `#9D7BEA` in dark mode; same in the App Clip's asset catalog), never system blue.
- Live updates (API-007): silent `content_updated` pushes drive them; `ContentView` adds a fallback `refreshBundle(silent: true)` poll at `AppState.liveRefreshInterval` (`LiveRefreshPolicy`: 60 s without a push token — not registered, registration failed, or the App Clip — 5 min safety poll with one, 15 s while the last refresh failed). No `isLoading` spinners for polls/pushes. Lives in shared code so the App Clip gets it too.
- Offline copy (API-007): every applied bundle is saved as one `SavedEvent` (raw bundle JSON + ETag + last refresh, atomic write) in `Application Support/attnd-event/event.json` (`EventStore`, excluded from backup) and restored at launch before any network, so the event opens offline. Network/server errors never clear it; only a 404 from the bundle (or lookup), leaving or switching events does (with the images). The App Clip uses the same code (the system may purge its storage).
- Image cache (API-007): `ImageStore` keeps location images, the logo(s) and the flyer (image or PDF) in `Application Support/attnd-images/<sha256(url)>.<ext>` — Application Support rather than Caches because Caches may be purged exactly when the attendee is offline at the venue; excluded from backup. After every applied bundle (and on restore) it prefetches every referenced URL (4 at a time; files older than 24 h are re-downloaded, keeping the old one on failure), then deletes files the bundle no longer references; ≤ 15 MB per file, 300 MB total (largest referenced files dropped first). Views use `CachedImage` (memory → disk → network), never `AsyncImage`; `FlyerView` loads the cached file into its `WKWebView` with a sniffed MIME type.

## Follow on Lock Screen (Live Activity), reminders, onboarding

Shared spec §7–8 (`glance_plan_spec`, same rules as Android's Live Update where they overlap); full app only, never in screenshot mode. Rules in `LiveFollowLogic.swift` (tests: `LiveFollowTests`, fixed `now`, America/Chicago), runtime in `LiveFollowController.swift`, views in `AttndWidgets/EventLiveActivity.swift`.

- **What it follows** (`LiveActivityPlanner.followDay`): today while one of its items hasn't ended (items still running from yesterday count for today), else the next event day; the plan's items of that day when one of them is still ahead (`planned`, `FollowDay.followsPlan`, content `follows_plan`), else the user's hearted items of that day when one of them is still ahead, else every item of the day (plan > hearts > now/next, like Android). One activity per event day (`EventActivityAttributes.dayStart`); ActivityKit's 8 h limit makes it restart each day.
- **Content** (`content`): current = the item in progress that started last; next / after = the next two not started yet, minus items the user skipped; walk minutes to the next location (`WalkTime` estimate, within 8 km); `opensAt` while the event's start (gates) is ahead today; `dayComplete` + count for the end-of-day summary (an activity whose day is over ends with the summary, dismissed after 30 min). `staleDate` = next change (current ends, next starts, gates open) + 1 min, else +1 h; views show "Open Attnd to update" when stale. Countdowns and progress are `Text(timerInterval:)` / `ProgressView(timerInterval:)`, so they tick without updates.
- **Start** (`decision`): from 2 h before the first followed item or the gates (whichever is first), on that day, while the app is in the foreground (scene activation, any change). Routed by `AttndApp.onOpenURL` → `AppState.openLiveActivityLink` (scheme `attnd-live` in `CFBundleURLTypes`; links for another event are ignored). Buttons (Lock Screen and expanded Dynamic Island only; compact/minimal regions are tap-to-open): Heart (current, else next), Skip (next), Dismiss (urgent).

## Planner ("My plan", shared spec §6)

A port of Android's planner rule for rule (`Planner.swift`, `PlanRequest.swift`; Android's `domain/Planner.kt` KDoc rules 1–12 are the source of truth) with the same fixture and expected numbers and plans (`AttndTests/PlannerFixture.swift`, `PlannerTests`, `PlanRequestTests`: DEMO-like festival, America/Chicago, Sat Nov 14 – Sun Nov 15 2026, now Sat 10:00 AM, hearted 101 + 114). Full app only; never in screenshot mode. Everything on the device.

- **Offered** only while the on-device model is available (`AppState.plannerAvailable` = `assistantAvailable`); otherwise no plan card, no planner in Ask, no onboarding plan card. An existing plan can still be viewed, re-planned from now, swapped and kept without the model (that is plain code).
- **Preferences** (`PlanPreferences`): liked/disliked tags and categories, `similarTo` ids, days, earliest/latest, duration, pace relaxed/balanced/packed, meals, kid-friendly. Foundation Models reads the request (`EventAssistant.planPreferences`: `PlanRequest.prompt` with NOW, DAYS, TAGS ≤ 40 by use, CATEGORIES, HEARTED, ITEMS ≤ 60 upcoming; `@Generable PlanPreferencesReply`, temperature 0) and `PlanRequest.validate` checks every value against the bundle exactly like Android's JSON `parse` (also kept, tested). `PlanRequest.heuristic` reads the request with plain rules; `merge(model, rules)` unions the sets (disliked wins), takes days/times/duration from the model when given, the model's pace unless balanced, ORs the booleans; the rules alone when the model fails.
- **Similarity**: TF-IDF cosine like Android (not NLEmbedding, so both platforms make the same plan): document = name + tags + location category + description + location name; terms = `PlanText.words` (Android's `SearchText`: NFD, marks dropped, lower case, letters/digits; not `EventSearch.words`, which also folds width and ß), ≥ 2 chars, Android's stop words; idf = ln((1+N)/(1+df)) + 1.
- **Scheduling** (`Planner`): score in integer milli-points, hearted must-includes with "or instead", gap = walk (Android's `Walking` estimate: whole seconds, then minutes rounded up; Android's haversine) + 5 min, pace cap 50/70/90 %, DP choice with Android's tie-breaks, lunch/dinner breaks with the nearest food location, reasons, ≤ 3 swap alternatives, `changed` via fingerprints, `summary` ("8 items, 10:00 AM – 11:00 PM, with a lunch break").
- **UI** (`PlanView.swift`): the Schedule tab's chips get **My plan** (before Hearted; `PlanStore.showsMyPlan`) while the planner is available or a plan exists. No plan: the request card (field, "Make My Plan", example chips). A plan: "Your plan changed" (Re-plan / Keep as Is) when a content update moved or removed a planned item, the request + summary with "Re-plan from Now" and "New Plan" (only with the model), then per day the items (time, name, place, reason; heart; Swap menu with "hearted" alternatives first) with walk legs ("4 min walk") and meal rows. Items open their detail like any schedule row.
- **Assistant**: My plan's header has "Open in Assistant"; rows swipe to Seen (check-off). In the assistant the plan is pinned on top and edited by text ("replace the 3pm thing with something like X", "I already ate", "done by 9", "chill version", …, `PlanEditor`), with `plan_diff` + Undo; shared plan links (`pendingSharedPlan`) open there with "Use this plan" / "Merge with mine" (`SharedPlans`). Siri: `PlanNextIntent` ("What's next on my plan"), `AlreadyAteIntent`, `SwapNextPlanItemIntent` (10 App Shortcuts, Apple's maximum).
- **Ask** (search sheet, screenshot mode / old path): a request that `PlanRequest.looksLikePlan` (plan/itinerary/highlights/"my Saturday"/"3 hours"/"kid friendly afternoon") makes the plan instead of answering: "Here's your plan: <summary>. It's in Schedule → My plan." + its items + **Open My Plan** (`AppState.showMyPlan`).
- **Stored** per event in UserDefaults `pref.plan.<event id>` (`PlanCodec` JSON, Android's shape, lenient), kept after leaving like hearts. Every change updates the Live Activity and reminders. Live Activity link `attnd-live://event/<id>/plan` opens My plan (the activity's fallback link when it follows the plan). No new usage metrics.

## Push Notifications

- The full app registers for remote notifications at **every launch** (`AppDelegate` → `AppState.registerForRemoteNotifications()`), whatever the opt-in: silent pushes need no permission (API-007). The hex token goes to `POST devices/` with `subscribed` = the Options opt-in; the server keeps the token even when `subscribed` is false. A missing token is omitted, never sent as `""` (that clears it on the server; `APIClient.nonEmpty`). Registration failure (`pushRegistrationDidFail`) switches the poll to 60 s. Not in screenshot mode or the App Clip.
- Enabling notifications in Options only requests alert authorization (and re-registers); turning it off sends `subscribed: false` and keeps the token.
- `type = "notification"` → alert (subscribed devices only); tapping opens the Updates tab for that event. With `priority = "urgent"` (API-011) the server sends it to every device with a token, time-sensitive, plus an ActivityKit `liveactivity` push to each registered `live_activity_token` (see Follow on Lock Screen).
- `type = "content_updated"` → silent (`content-available`), sent to every device in the event with a token (debounced, ≤ 1 per 15 s per event). `handlePush` refetches only when its `content_version` is newer than the shown bundle's (`ContentUpdatePolicy`), after a random 0–10 s delay, in the foreground or background; `didReceiveRemoteNotification` returns after the fetch and the save to disk. A push that wakes a terminated app restores the saved event first. Requires the `remote-notification` background mode (in `Info.plist`).
- `aps-environment` is `development` in `Attnd.entitlements`; distribution signing switches it to production.

**iPhone Duo is brand new (released late Oct 2026): always check online for the latest Apple docs,
Xcode/simulator release notes and App Store Connect behaviour before working on anything Duo-related —
don't rely on model training data.** As of Nov 14, 2026: Duo screenshots (inner 2007×2853, outer 1398×2034)

## Deep Linking (Universal Links)

`https://attnd.app/join/<event_code>/` → `AppState.handleDeepLink(_:)` → `join(code:)`: looks the event up, leaves any current event, then joins. The App Clip uses the same URL.

Shared plan links (API-015, the AASA claims `/p/*` for the app and the App Clip): `https://attnd.app/p/<EVENT_CODE>/<payload>` (trailing `/` optional; payload = base64url without padding of `{"v":1,"ids":[…],"d":"YYYY-MM-DD"}`, ≤ 1,500 characters) → `SharedPlanLink.parse` → join the event, then (full app only, payload of the right alphabet and length) `AppState.pendingSharedPlan` for the assistant's read-only "Shared plan". A payload the app can't read just joins; the App Clip only joins. A scanned QR code of such a link joins too (`DeepLink.eventCode(fromScanned:)`).

In Xcode, put them in the scheme's Test environment locally (never commit a key). Device ids are `ci-ios-<run id>-<random>` and every test leaves the event. If the server's demo data changes, attnd-web's test of `load_demo_event` is the source of truth; update the three repos together.
