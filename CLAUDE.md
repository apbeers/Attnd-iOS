# Attnd iOS

SwiftUI app that lets attendees discover and follow live events. Consumes the Attnd REST API v2 served by **[attnd-web](https://github.com/apbeers/Attnd-Web)** (contract: [`API_V2.md`](https://github.com/apbeers/Attnd-Web/blob/develop/API_V2.md) in attnd-web).


## Branching (initial development)

- `main` = production (default branch), `develop` = dev/beta. Pushing to `develop` deploys to the dev server / TestFlight / Play internal testing; pushing to `main` deploys to production.
- **While there are no real users yet, commit and push straight to `develop`** — no feature branches or PRs needed. Merge `develop` → `main` to release. Revisit this once the apps have users.


## API changes start in attnd-web

attnd-web is the coordinating repo. The API contract ([`API_V2.md`](https://github.com/apbeers/Attnd-Web/blob/develop/API_V2.md)) and the cross-repo tracker ([`API_CHANGES.md`](https://github.com/apbeers/Attnd-Web/blob/develop/API_CHANGES.md)) live there only; this repo has no copy.
- Don't build against API behaviour that isn't in `API_V2.md`. If a feature needs an API change, add it in attnd-web first (tracker entry, server, contract), then implement the app part here.
- Implement what the tracker entry's app section says. Put its ID in the commit message (e.g. `API-003: …`), then tick this app's column in attnd-web's `API_CHANGES.md`.
- Keep decoding lenient: ignore unknown keys and default missing ones, so additive server changes never break shipped builds.

## Dependency Policy

**Apple frameworks only; no third-party packages.** No SPM, CocoaPods or Carthage dependencies, no Firebase. Push uses APNs directly via `UIApplication` / `UserNotifications`.

## Tech Stack

- **Swift 6 / SwiftUI** — iOS 26+, Swift 6 language mode, `@Observable` + `@MainActor` state
- **URLSession** — networking
- **Apple App Attest** — device attestation for API authentication in production
- **APNs** (`UserNotifications`) — organizer notifications and silent `content_updated` pushes
- **DataScannerViewController** (VisionKit) — QR code scanning
- **MapKit** — map view
- **Foundation Models** — the event assistant on the plan page (streamed turns with tool calling), "Ask about this event", the planner's preference extraction (structured output) and the plan page's day summaries, with Apple Intelligence's on-device model (the plan page, planner and assistant exist only when the model is available)
- **ActivityKit + WidgetKit** (`AttndWidgets` extension in the app, `AttndClipWidgets` in the App Clip, the same sources) — "Follow on Lock Screen" Live Activity, Dynamic Island, Apple Watch Smart Stack
- **Core Image** — QR codes for shared plan links (`ShareCard`)
- **UserNotifications** (local) — reminders before liked / planned items and the "tap to follow" notification. No BackgroundTasks and no `CLMonitor` (background app refresh and "Tell me when I arrive" were removed Nov 19, 2026: App Clips can't run background tasks, and the app and the clip are the same)
- **os (`Logger`, `OSSignposter`) + Network (`NWPathMonitor`)** — structured logging, signposts; **MetricKit** — crash/hang reports. See Logging & diagnostics
- **Xcode project**: `Attnd.xcodeproj` in Xcode 27.2's JSON format (`project.xcproj`, converted on Nov 14, 2026 with `xcodebuild -convert-project "Xcode Project"` on Xcode 27.2; JSON with trailing commas — edit carefully or in Xcode; `-convert-project pbxproj` converts back). **Xcode 27.2** (build 27B52) is required: the JSON project format needs 27.2 and the iPhone Duo APIs need 27.1. CI pins it with `XCODE_VERSION` (repo variable, default `27.2`) on the `xcode-27` runner; bump it when a newer release lands on the image. Xcode Cloud is not used (it would number builds independently and collide with CI's).
- **Build configurations**: `Debug` (local), `Dev` (a copy of Debug **optimised for size like Release** (`-Osize`, C `-Os`, testability off; Nov 19, 2026 owner: the App Clip carries the whole app and must stay under Apple's 15 MB limit in TestFlight builds too — the unoptimised clip was ~20 MB of code), with the `DEBUG` + `DEV` Swift conditions and `DEBUG=1 DEV=1` preprocessor macros, assertions on, `dwarf-with-dsym` (crash reports symbolicate), `ENABLE_DEBUG_DYLIB = NO` and product validation; `Config/Dev.xcconfig` includes `Debug.xcconfig`; for all targets, the tests inherit it; `Debug` stays `-Onone` for local debugging), `Release` (**`-Osize`**: the App Store build is the one that must stay small). CI archives **Dev for `develop`** (TestFlight builds with debug flags, continuous log upload) and **Release for `main`**; both are distribution-signed by the export.
- **Targets**: `Attnd` (iPhone only, including iPhone Duo; all orientations; no iPad), `AttndAppClip` (`com.arcu.Attnd.clip`), `AttndWidgets` (widget extension `com.arcu.Attnd.widgets`, embedded in `Attnd` by the "Embed Foundation Extensions" copy phase, `bundle-base-path: plugins-directory`), `AttndClipWidgets` (widget extension `com.arcu.Attnd.clip.widgets`, embedded in `AttndAppClip` the same way: an App Clip may only embed extensions whose bundle id starts with its own, so it can't share `AttndWidgets`), `AttndTests`. Both widget extensions are the Live Activity only (the "Now & Next" Home Screen widget was removed Nov 19, 2026), compile the same sources (the `AttndWidgets/` folder plus `LiveActivityModel.swift` / `LiveActivityIntents.swift`), use `Config/*.xcconfig` for `IOS27_SDK` and have their own empty entitlements (`AttndWidgets/AttndWidgets.entitlements`, `AttndWidgets/AttndClipWidgets.entitlements`, both excluded from the synchronized folder's membership) so they don't inherit the app's
- **Entitlements**: no WeatherKit (removed Nov 19, 2026 with the weather: WeatherKit isn't offered for App Clip App IDs) and **no App Group** (the "Now & Next" widget was its only user). The app and the clip both have `aps-environment`, associated domains (`applinks:` / `appclips:`) and App Attest; the app also Time Sensitive Notifications. CI signs manually (see CI/CD → Signing); automatic signing with the API key had failed on the App Group.
- **Build settings note**: the `Attnd` and `AttndAppClip` targets and both widget extensions run Xcode's App Intents metadata step (the Live Activity buttons are `LiveActivityIntent`s; don't skip it there). `LM_SKIP_METADATA_EXTRACTION = YES` is set only on `AttndTests`. **The app and the App Clip are identical** (owner, Nov 19, 2026: "nothing in one that isn't in the other"): they compile the same source files (keep `project.xcproj` membership identical for `Attnd/compile-sources` and `AttndAppClip/compile-sources`), the clip defines no `APP_CLIP` condition and there is no `#if APP_CLIP` in the code; what still differs is listed under App Clip. CI prints a deduplicated warnings summary (`scripts/ci/warnings.py`) after every xcodebuild; keep it at zero.

## App icon

The app icon is a classic `AppIcon.appiconset` in each target's asset catalog (`Attnd/Assets.xcassets`, `AttndAppClip/Assets.xcassets`, the same PNGs; `ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon`). ## App Flow

```
Launch
├── registerForRemoteNotifications() (app and App Clip, every launch, opt-in or not)
├── POST devices/ (registration, push token if any — never "", subscribed = alert opt-in)
├── Saved copy on disk for the saved event code? → shown at once (works offline), then
│   POST join/ + GET bundle/ in the background (join retried after a later successful refresh)
├── Else saved event code? → GET events/lookup/?q=<code> → join silently
│   └── 404 → code forgotten; offline / none saved → LaunchScreen
│
LaunchScreen
├── GET events/nearby/?lat=&lng=
├── QR scan / search → GET events/lookup/?q=<code or exact name>
│
Join event
├── POST events/<id>/join/ {device_id, platform: "ios", push_token, app_version}
└── GET events/<id>/bundle/ (If-None-Match, X-Device-Id)
│
ContentView (TabLayout: display.tabs — Map · Places · Schedule · Flyer · Updates, default_tab)
├── "My plan" button → the plan page, a full-screen cover (only with the on-device model; otherwise, and in screenshot mode: search button → Search sheet); Options sheet
```

## Usage reporting (API-005)

- Anonymous counts only: `POST events/<id>/usage/` with `{"platform": "ios", "events": [{name, detail?, count, at}]}`. **Never** a device ID, any identifier, or search text.
- Call sites use `appState.track(.metric, detail:)` / `track(.metric, id:)`; it is a no-op outside an event. `UsageReporter` (main actor, in `AppState.swift`) aggregates in a pure `UsageAggregator` (`Models.swift`) keyed by (event, name, detail, UTC 5-minute bucket; `at` = start of the bucket, e.g. `2026-11-14T16:05:00Z`) and flushes at most every 60 s, when the scene goes to the background (`AppRootView`) and before leaving or switching events. A failed batch is retried once on the next flush, then dropped; errors are never shown. Max 200 entries per request.
- Hearts (API-009): `location_heart` / `location_unheart` (detail = location id) and `schedule_item_heart` / `schedule_item_unheart` (detail = item id), counted by `AppState.setHeart` (rows, details, map card, search, peeks, the assistant, Live Activity buttons) only when the state actually changes. Older servers drop unknown names harmlessly.
- Instrumented: `app_open` (silent rejoin at launch; scene becomes active in `ContentView`), `tab_view` (`selectedTab` didSet; nothing for the plan page; the opening tab when the first bundle is applied; `options` when the Options sheet opens, `presentedSheet` didSet), `location_view` / `schedule_item_view` (`.task(id:)` on `LocationDetailView` / `ScheduleItemDetailView`, so every route counts), `notification_open` (`handlePush(opened: true)`), `search` (`SearchUsageCounting`, used by `SearchableIf` and the search sheet: on submit, or once a non-empty query settles for 1.5 s; no detail, never the text), no `tab_view` for the search sheet (`EventSheet.search.usageDetail` is nil: the server accepts only the event tabs and `options`), `refresh` (`AppState.pullToRefresh()` from every `.refreshable` in an event).

## Logging & diagnostics (API-013, API-014)

Shared spec with Android and attnd-web; the record format and **every event name** are in attnd-web `LOG_EVENTS.md` (only names listed there may be logged; add a row there first), the endpoints in `API_V2.md` → Diagnostics. Tests: `AttndTests/LoggingTests.swift` (redaction, record keys, gzip/CRC-32, debug codes, perf buckets, upload body, `Retry-After`, ring buffer).
- **Facade** `AppLog.debug/info/…(.cat, "event.name", "msg", [fields])`: message and fields are autoclosures, built only when the level is captured (`LogCore.isEnabled`, one `NSLock`); the record (seq, ts with ms, `mono_ms` from `ContinuousClock` since launch, app/build/os/model, `state` fg/bg from the scene phase, `net` from `NWPathMonitor`, `event_id`, `diag`) is encoded and written on one serial utility queue. Each record also goes to `os.Logger` (subsystem `com.arcu.Attnd`, category = `cat`; event name public, text public only in Debug/Dev builds). `AppLog.caught(error, .cat, "where")` logs `error.caught` (domain, code, type, where); use it in every `catch` that would otherwise be silent.
- **Redaction** (`LogRedaction`): never search/Ask/plan text in production (`textFields` → `query_len`; Debug/Dev builds add `query`), never tokens, keys, push / Live Activity tokens, JWTs, emails, the device id or support code (`scrub` runs on every message and string field: URL queries, bearer tokens, JWTs, emails, UUIDs, long hex, `key=value` secrets); URLs as path templates (`events/{id}/bundle/`); coordinates rounded to 0.01°. The debug code is never in support info or `devices/`.
- **Levels** (`LogPolicy`): Debug and Dev builds `debug` (disk); production (Release) captures **errors only** (`error`, `fault`; `LogPolicy.captureLevel`) and keeps them on disk, with no in-memory pre-roll, and uploads nothing. Note that `AppLog.caught` defaults to `warning`, so caught errors that matter in production need `level: .error`.
- **Ring buffer** (`LogStore`): `Application Support/attnd-logs/current.jsonl` + `previous.jsonl` (1 MB each, rotated, excluded from backup); `seq` continues across launches (read from the file's tail).
- **Uploads** (`LogUploader`): Dev builds always (`reason: "dev"`, one code per install in `log.devCode`), production only in debug mode (`reason: "debug_mode"`, the App Clip too); never in screenshot mode. `POST /api/v2/diagnostics/logs/`, gzip (`Content-Encoding: gzip`), ≤ 500 entries / 256 KB of JSON per request (a 413 halves the batch), every ~10 s (debug mode) / ~30 s or 200 records (Dev), and when the scene goes to the background; a `429`'s `Retry-After` is honoured (an older server's 404 waits an hour); failures back off and keep the lines. The cursor (last uploaded `seq`) is `log.upload.cursor`. Uploads aren't logged as requests (only `logging.upload`).
- **Request headers** (`APIClient.perform`): every call (retries too) a new `X-Request-Id` (32 hex), logged as `req_id` in `net.request.started/finished/failed`; `X-Diag-Session: D-XXXXX` while a session uploads. Failures and HTTP ≥ 400 (except the first 401) count `perf_api_error`.
- **Debug mode** (Options → About & Support → "Turn On Debug Logging for 10 Minutes", production, never remote): a new `D-XXXXX` (Crockford base32, `DebugCode`), Copy, countdown, Turn Off; level `debug` + upload for 10 min, from the moment it is turned on (nothing from before: no pre-roll); code/expiry/start in `log.debugMode.*`, so it survives restarts and turns itself off (`logging.debug_mode`). Viewer: "Logs" in Debug/Dev builds, "Recent Logs" in production (the errors on disk, plus whatever a debug session captured); not in screenshot mode.
- **Signposts** (`AppSignpost`, Instruments category `perf`, also `perf.signpost`): `launch`, `bundle_fetch` (request → decoded), `planner` (the Planner run), `map_first_render` (Map tab appears → first `onMapCameraChange(.onEnd)`).
- **Perf counts (API-014)** through `PerfMetrics` → `UsageReporter` (the joined event's batch, or the next one; ≤ 50 waiting): `perf_bundle_fetch` / `perf_bundle_304`, `perf_api_error`, `perf_push_refresh_delay` (`content_updated` → applied), `perf_live_start_fail` (disabled/limit/error), `perf_planner_ms`, `perf_map_first_render`; `perf_launch_cold` / `perf_launch_warm` measured by `LaunchTiming` (process start → first frame / background → active) in the app and the App Clip alike (MetricKit's daily launch histograms are no longer used, Nov 19, 2026). Labels exactly as the server's (`PerfBucket`, e.g. `<0.5s`, `>=4s`).
- **MetricKit** (`MetricKitReporter`, app and App Clip, not in screenshot mode; whether MetricKit delivers diagnostics to an App Clip is unverified): crash, hang, CPU, disk-write and launch diagnostics → `POST diagnostics/reports/` (`kind`, `occurred_at`, per-report build/os/model, `summary`, `reason`, `exception`, `payload` = `jsonRepresentation()`, `diag` while a session uploads; no identifier), stored in `attnd-logs/reports/` until sent (≤ 20, ≤ 7 days). Daily metric payloads are never uploaded. Symbolication: the admin panel dispatches `symbolicate.yml` with the build's `dsyms-<build>` artifact.
- **App Privacy** (App Store Connect): Diagnostics → Crash data, Performance data, Other diagnostic data: not linked to identity, not used for tracking.

- All times are displayed in the **event's** `timezone` (`EventTimeFormat`), never the device's.

When set, `EventWebsiteLink` (a `Link`, so `openURL` → Safari, never an in-app web view; nothing from the app goes to it) shows **Website** under the event header in Options and in `EventInfoView` (search's event result); not in any tab bar, not in screenshots.

Decoded leniently into `EventContext` / `LocationContext` / `ScheduleItemContext` (`Models.swift`: missing parts default, list entries without their required part dropped, empty objects → nil). Used by the on-device assistant (tools, retrieval, item lines), search (performer names and genres weigh like tags, bios like descriptions, in `EventSearch` and `AssistantSearch`) and the detail screens (`ContextViews.swift`). Offline automatically (the saved bundle is the raw JSON).
- Tags (API-010): `Location.tags` and `ScheduleItem.tags` arrive lower case (`"live music"`); filter and search on them as sent, show them through `TagText` ("Live music · Free"). Location tags are searched like item tags (weight 2).
- `AppNotification.priority` (API-011): `urgent` (anything else or missing = `normal`) is shown with a red "Urgent" label and a red-tinted row in Updates, and for 12 h (until dismissed) as the prominent red `UrgentUpdateBanner` above the other tabs and in the Live Activity's urgent block.
- `display.accent_color` (or the event's) tints the app. Otherwise the tint is the asset `AccentColor` (brand purple `#431F86`, `#9D7BEA` in dark mode; same in the App Clip's asset catalog), never system blue.
- Live updates (API-007): silent `content_updated` pushes drive them; `ContentView` adds a fallback `refreshBundle(silent: true)` poll at `AppState.liveRefreshInterval` (`LiveRefreshPolicy`: 60 s without a push token — not registered or registration failed — 5 min safety poll with one, 15 s while the last refresh failed). No `isLoading` spinners for polls/pushes.
- Offline copy (API-007): every applied bundle is saved as one `SavedEvent` (raw bundle JSON + ETag + last refresh, atomic write) in `Application Support/attnd-event/event.json` (`EventStore`, excluded from backup) and restored at launch before any network, so the event opens offline. Network/server errors never clear it; only a 404 from the bundle (or lookup), leaving or switching events does (with the images). The App Clip uses the same code (the system may purge its storage).
- Image cache (API-007): `ImageStore` keeps location images, the logo(s) and the flyer (image or PDF) in `Application Support/attnd-images/<sha256(url)>.<ext>` — Application Support rather than Caches because Caches may be purged exactly when the attendee is offline at the venue; excluded from backup. After every applied bundle (and on restore) it prefetches every referenced URL (4 at a time; files older than 24 h are re-downloaded, keeping the old one on failure), then deletes files the bundle no longer references; ≤ 15 MB per file, 300 MB total (largest referenced files dropped first). Views use `CachedImage` (memory → disk → network), never `AsyncImage`; `FlyerView` loads the cached file into its `WKWebView` with a sniffed MIME type.

## Offline (backend down during the event)

Once the event was loaded, everything works with no server: the saved bundle opens at launch before any network (a deep link waits for it, so `/join/` and `/p/` links to the joined event need no lookup), all tabs, search, the plan page (router, planner, proposals, undo, the day summaries; the model is on-device), API-018 context (part of the saved bundle JSON), likes, Live Activity content and reminders (local), cached images and flyer, share links / QR (built locally), Options. Requests never block the UI and never clear local state (only a bundle 404, leaving or switching does). Queued until the server answers again: the join (after the next successful refresh), `POST devices/` (`deviceSyncPending`, same), `POST leave/` (`pref.pendingLeaves`, at launch and after a refresh), usage counts (one retry, then dropped), diagnostics logs and MetricKit reports (on disk). Needs the network by nature: map tiles (MapKit; pins and estimates still show), MKDirections routes (dashed estimate instead), joining a new event, nearby events, App Attest. Server work that must survive an outage goes through `AppState.retryPendingServerWork`.

## Glance, distance and hearts ("likes")

User-facing text says **like / liked / likes** (assistant spec §0: "Like", "Liked" chips); the heart icon stays, and identifiers, storage keys (`heartedScheduleItems`, …) and the API-009 metric names (`location_heart`, …) keep "heart". Planner reasons say "You liked this" / "Because you liked X" / "At X, which you liked" (plus "You added this", "Liked by 3 of you").

Everything here is local (no server change except the API-009 heart metric names). Rules and tests are shared with Android (`Glance.swift`, `GlanceTests`; fixed `now`, America/Chicago, `en_US`).

- **Relative times** (`RelativeTimeText`): "Ended", "Started 20 min ago" (< 1 h; "Started just now" < 1 min), "Now" (" · ends 8:30 PM" in details/peeks), "Starting now" (< 1 min), "in 12 min", "in 3 h 20 min" (< 6 h, " 0 min" dropped), then by calendar day in the **event's** zone: "today 7:30 PM", "tomorrow 7:30 PM", "in 3 days" (< 7), "in 2 weeks" (< 35 days), "in 4 months" (< 12), "in 1 year". - **Walking route** (map card, `WalkingRouteProvider`): with permission and the user within 8 km of the selected pin, `MKDirections` (`.walking`, never navigation) → `MapPolyline` + "12 min walk · 0.6 mi". No route, an error, or a route > 2.5× the straight line (festival grounds) → a dashed straight line + "about 8 min walk" (straight × 1.2 at 1.3 m/s, minutes rounded up). ## Follow on Lock Screen (Live Activity), reminders, onboarding

Shared spec §7–8 (`glance_plan_spec`, same rules as Android's Live Update where they overlap); the app and the App Clip (the clip through its own `AttndClipWidgets` extension), never in screenshot mode. Rules in `LiveFollowLogic.swift` (tests: `LiveFollowTests`, fixed `now`, America/Chicago), runtime in `LiveFollowController.swift`, views in `AttndWidgets/EventLiveActivity.swift`.

- **What it follows** (`LiveActivityPlanner.followDay`): today while one of its items hasn't ended (items still running from yesterday count for today), else the next event day; the plan's items of that day when one of them is still ahead (`planned`, `FollowDay.followsPlan`, content `follows_plan`), else the user's hearted items of that day when one of them is still ahead, else every item of the day (plan > hearts > now/next, like Android). One activity per event day (`EventActivityAttributes.dayStart`); ActivityKit's 8 h limit makes it restart each day.
- **Content** (`content`): current = the item in progress that started last; next / after = the next two not started yet, minus items the user skipped; walk minutes to the next location (`WalkTime` estimate, within 8 km); `opensAt` while the event's start (gates) is ahead today; `dayComplete` + count for the end-of-day summary (an activity whose day is over ends with the summary, dismissed after 30 min). `staleDate` = next change (current ends, next starts, gates open) + 1 min, else +1 h; views show "Open Attnd to update" when stale. Countdowns and progress are `Text(timerInterval:)` / `ProgressView(timerInterval:)`, so they tick without updates.
- **Start** (`decision`): from 2 h before the first followed item or the gates (whichever is first), on that day, while the app is in the foreground (scene activation, any change). Before that, from the foreground, it is **scheduled** with iOS 26's `Activity.request(…, style:, alertConfiguration:, start:)` (the system starts it at that time even in the background, with an alert; only ≤ 36 h ahead; the start time is remembered in `pref.liveActivity.scheduledStarts`, so a changed time replaces the pending one). Checked Nov 15, 2026: iOS 26/27 still allow no other background start except a `LiveActivityIntent` or a push-to-start, so when scheduling isn't possible (app in the background, or ActivityKit refused) a local notification at that time says "Prairie Lights in 2 h · tap to follow on your Lock Screen" (`FollowPromptText`, category `attnd.follow`); tapping it opens the app at the item and starts the activity (`forcedDay` skips the 2 h lead for today). "Start Now" in Options does the same.
- **Running late** (assistant spec §6): when following the plan and the user is > 100 m from the next item's location at its departure time (`LiveAssist.runningLate`), the content gets `leave_by` + `late_state` (`leave_now` / `cant_make_it`) and the Up next row says "Leave now" / "Running late". The assistant shows the same as a live hint with Directions / swap chips; auto check-off (≥ 10 min within 150 m while it ran, from position samples while a screen already tracks the location), skipped items, gap fillers, organizer changes and the day's recap are hints there too.
- **Updates**: every applied bundle (so the silent `content_updated` push), hearts, skips, location changes (walk minutes) and the buttons; identical content is not re-sent. No background app refresh (removed Nov 19, 2026: App Clips can't run background tasks; between foreground visits the activity's own timers tick and silent pushes refresh it).
- **Links and buttons**: the whole activity → Updates at the urgent announcement, else the current / next item (Schedule); "Map" → the Map tab at the next location (the card draws the walking route); the urgent block → Updates at it. Routed by `AttndApp.onOpenURL` → `AppState.openLiveActivityLink` (scheme `attnd-live` in `CFBundleURLTypes`; links for another event are ignored). Buttons (Lock Screen and expanded Dynamic Island only; compact/minimal regions are tap-to-open): Heart (current, else next), Skip (next), Dismiss (urgent).
- **Urgent (API-011)**: activities start with `pushType: .token` (falling back to none); each token from `pushTokenUpdates` (hex) goes to `POST devices/` as `live_activity_token`, `null` when that activity ends or following is turned off (`AppState.setLiveActivityToken`, retried with the next `syncDevice`). The server's ActivityKit push replaces the content state with `{"urgent": {...}}` only; the app's next update refills the rest and keeps `urgent` (the bundle's newest urgent announcement ≤ 12 h old, else the pushed one) until dismissed or 12 h old. A new urgent block in a local update alerts (lights the screen). Urgent announcements also get the red-tinted `UrgentUpdateBanner` above every tab except Updates (takes the newest-update banner's place; dismissed per event in `EventPersonalState.dismissedUrgentIds`). The **Time Sensitive Notifications** entitlement (`com.apple.developer.usernotifications.time-sensitive`) is in `Attnd.entitlements` only (not the clip's: unverified that App Clip App IDs offer it; without it the clip's alerts arrive as active, not time-sensitive) (the urgent alert push uses `interruption-level: time-sensitive`; reminders are time-sensitive too).
- **Views**: Lock Screen (urgent block first, Now + progress, Up next + countdown + walk, "Then …", buttons; StandBy uses it too), Dynamic Island compact (icon + countdown; on iOS 27 an icon when `isDynamicIslandLimitedInWidth`, behind `IOS27_SDK`), minimal (progress ring or icon), expanded (now / next / buttons, or the urgent block), `.supplementalActivityFamilies([.small])` for Apple Watch Smart Stack and CarPlay. Times in the event's zone.
- **Options**: "Follow on Lock Screen" per event (`EventPersonalState.followOnLockScreen`; default on once something is hearted or planned, `AppState.followsOnLockScreen`), "Start Now". "Tell Me When I Arrive" (the `CLMonitor` venue circle, Always location) was removed everywhere Nov 19, 2026 (owner); old `notifyOnArrival` / `arrivalPromptDay` values are ignored and `pref.venueMonitorKey` is deleted at launch.
- **Reminders** (`ReminderPlanner`): 15 min before each hearted or planned item, "Prairie Lights in 15 min · 8 min walk" (walk from the last known position, within 8 km and > 20 m) / "Main Stage · 7:30 PM", category `attnd.reminder`, only with the notification opt-in and permission, at most 40, rescheduled (ids `attnd.reminder.<event>.<item>`) whenever hearts, content or the opt-in change and removed outside an event. Local notifications carry `attnd_local` / `attnd_event` / `attnd_item` (never `type`), so `PushPayload` ignores them; `AppDelegate` sends their taps to `LiveFollowController.handleNotificationTap`.
- **Onboarding** (`OnboardingView`, `EventSheet.tour`): after the first join on the device (`pref.onboardingSeen`; `AppState.pendingTour` → ContentView presents it), skippable, reopened from Options → Tour, never in screenshot mode. Cards: what you can do; location (prompt); notifications (prompt); "Plan your day" only when `AppState.plannerAvailable` (Apple Intelligence on-device model; never in screenshot mode) with `PlanRequest.examples` (Android's: "Plan my <weekday> around <top tag> and <next tag>" from schedule tags, skipping general/free/music/demo and family tags; "I've got 3 hours, show me the highlights"; "Kid-friendly afternoon" when an item has a family tag; the question "What's on near me right now?"). A plan chip makes the plan and opens the plan page (`AppState.useExample`); the question opens the search sheet and asks the model at once (`showSearch(_:ask:)` → `autoAskQuery`).
- **App Clip**: the same Live Activity, reminders, "tap to follow" notification and Live Activity push token as the app (`AttndClipWidgets` draws it; App Clips may offer Live Activities only through a widget extension of their own). ActivityKit may refuse a scheduled start in a clip; the code falls back to the "tap to follow" notification like the app when the system says no.

## Planner ("My plan", shared spec §6)

A port of Android's planner rule for rule (`Planner.swift`, `PlanRequest.swift`; Android's `domain/Planner.kt` KDoc rules 1–12 are the source of truth) with the same fixture and expected numbers and plans (`AttndTests/PlannerFixture.swift`, `PlannerTests`, `PlanRequestTests`: DEMO-like festival, America/Chicago, Sat Nov 14 – Sun Nov 15 2026, now Sat 10:00 AM, hearted 101 + 114). The app and the App Clip; never in screenshot mode. Everything on the device.

- **Offered** only where the plan page exists (`AppState.plannerAvailable` = `hasPlanPanel`: the app or the App Clip, not screenshot mode, **with the on-device model**; planner_view_spec §1). `makePlan` falls back to `PlanRequest.heuristic` alone and the likes only when the model fails for a request.
- **Preferences** (`PlanPreferences`): liked/disliked tags and categories, `similarTo` ids, days, earliest/latest, duration, pace relaxed/balanced/packed, meals, kid-friendly. Foundation Models reads the request (`EventAssistant.planPreferences`: `PlanRequest.prompt` with NOW, DAYS, TAGS ≤ 40 by use, CATEGORIES, HEARTED, ITEMS ≤ 60 upcoming; `@Generable PlanPreferencesReply`, temperature 0) and `PlanRequest.validate` checks every value against the bundle exactly like Android's JSON `parse` (also kept, tested). `PlanRequest.heuristic` reads the request with plain rules; `merge(model, rules)` unions the sets (disliked wins), takes days/times/duration from the model when given, the model's pace unless balanced, ORs the booleans; the rules alone when the model fails.
- **Similarity**: TF-IDF cosine like Android (not NLEmbedding, so both platforms make the same plan): document = name + tags + location category + description + location name; terms = `PlanText.words` (Android's `SearchText`: NFD, marks dropped, lower case, letters/digits; not `EventSearch.words`, which also folds width and ß), ≥ 2 chars, Android's stop words; idf = ln((1+N)/(1+df)) + 1.
- **Scheduling** (`Planner`): score in integer milli-points, hearted must-includes with "or instead", gap = walk (Android's `Walking` estimate: whole seconds, then minutes rounded up; Android's haversine) + 5 min, pace cap 50/70/90 %, DP choice with Android's tie-breaks, lunch/dinner breaks with the nearest food location, reasons, ≤ 3 swap alternatives, `changed` via fingerprints, `summary` ("8 items, 10:00 AM – 11:00 PM, with a lunch break").
- **UI**: the **plan page** (the floating My plan button; see Search and the plan page for the page, the text box, previews, Change sheet, bottom bar and the wide layout). No plan: the examples (`PlanRequest.examples`) and the likes, the text box focused; a plan request builds the plan in place (progress on the page). The Schedule list has no My plan chip.
- **Shared plan links** (`pendingSharedPlan`, ContentView) open the plan page with a proposal "Use This Plan" / "Merge with Mine" (`SharedPlans`).
- **Ask** (search sheet, screenshot mode / old path): a request that `PlanRequest.looksLikePlan` (plan/itinerary/highlights/"my Saturday"/"3 hours"/"kid friendly afternoon") makes the plan instead of answering: "Here's your plan: <summary>. It's in My plan." + its items + **Open My Plan** (`AppState.showMyPlan`: the plan page; without the model there is no planner, so this path only runs where the plan page exists).
- **Stored** per event in UserDefaults `pref.plan.<event id>` (`PlanCodec` JSON, Android's shape, lenient), kept after leaving like hearts. Every change updates the Live Activity and reminders. Live Activity link `attnd-live://event/<id>/plan` opens the plan page (the Schedule tab without the model) (the activity's fallback link when it follows the plan). No new usage metrics.

## Push Notifications

- The app and the App Clip register for remote notifications at **every launch** (`AppDelegate` → `AppState.registerForRemoteNotifications()`), whatever the opt-in: silent pushes need no permission (API-007). The hex token goes to `POST devices/` with `subscribed` = the Options opt-in; the server keeps the token even when `subscribed` is false. A missing token is omitted, never sent as `""` (that clears it on the server; `APIClient.nonEmpty`). Registration failure (`pushRegistrationDidFail`) switches the poll to 60 s. Not in screenshot mode. The clip asks for ephemeral notifications (`NSAppClipRequestEphemeralUserNotification`, 8 h, no prompt) and has the normal opt-in in Options. **App Clips may not declare `UIBackgroundModes`** (App Store Connect rejects the upload), so the clip gets no silent `content_updated` pushes: `LiveRefreshPolicy.canReceivePush` also needs the `remote-notification` background mode in the bundle's Info.plist (`declaresSilentPush`), so the clip keeps the 60 s poll; its alerts (organizer and urgent notifications) still arrive.
- Enabling notifications in Options only requests alert authorization (and re-registers); turning it off sends `subscribed: false` and keeps the token.
- `type = "notification"` → alert (subscribed devices only); tapping opens the Updates tab for that event. With `priority = "urgent"` (API-011) the server sends it to every device with a token, time-sensitive, plus an ActivityKit `liveactivity` push to each registered `live_activity_token` (see Follow on Lock Screen).
- `type = "content_updated"` → silent (`content-available`), sent to every device in the event with a token (debounced, ≤ 1 per 15 s per event). `handlePush` refetches only when its `content_version` is newer than the shown bundle's (`ContentUpdatePolicy`), after a random 0–10 s delay, in the foreground or background; `didReceiveRemoteNotification` returns after the fetch and the save to disk. A push that wakes a terminated app restores the saved event first. Requires the `remote-notification` background mode (in `Info.plist`).
- `aps-environment` is `development` in `Attnd.entitlements` and `AttndAppClip.entitlements`; CI sets both to production for the App Store profiles.
- **App Clip topic (API-019)**: the clip's bundle id is `com.arcu.Attnd.clip`, so its tokens need that APNs topic (and `com.arcu.Attnd.clip.push-type.liveactivity`). `join/` and `devices/` bodies always carry `app_clip` (`APIClient.isAppClip`: `Bundle.main.bundleIdentifier` ends in `.clip`, decided at runtime, no compile-time switch; `true` from the clip, `false` from the app), and the server sends each device's pushes on its own topic.

## App Clip

**The App Clip is the app** (owner, Nov 19, 2026: people will mostly scan the code at the event, use Attnd for a few hours or days and never look at it again, so the clip gets everything; "the App Clip and the main app should be identical"). `AttndAppClip` compiles exactly the same `Attnd/` sources as `Attnd`, including the entry point (`AttndApp.swift` + `AppDelegate.swift`; `AttndAppClipApp.swift` is gone), the plan page / planner / assistant / Foundation Models, push, the Live Activity and reminders, MetricKit and the logging files. There is no `APP_CLIP` compilation condition and no `#if APP_CLIP`. **Every new `.swift` file in `Attnd/` goes into both `Attnd/compile-sources` and `AttndAppClip/compile-sources`** in `project.xcproj` (the `Attnd` group and its `Components` subgroup are plain groups, not synchronized). `AttndAppClip/` holds only the clip's `Info.plist` (ephemeral notifications, `remote-notification`, `NSSupportsLiveActivities`, the `attnd-live` URL scheme, the same camera / location texts), `AttndAppClip.entitlements` (`appclips:attnd.app`, App Attest, parent app, `aps-environment`) and its asset catalog.

What still differs (and why):
- **Bundles**: the clip embeds `AttndClipWidgets` (`com.arcu.Attnd.clip.widgets`) instead of `AttndWidgets` (an App Clip can only embed extensions prefixed by its own bundle id); same sources. App Store Connect requires an App Clip's extension to carry `com.apple.developer.on-demand-install-capable` (only that key, in `AttndClipWidgets.entitlements`), so its App ID has the On Demand Install Capable capability ticked (no Configure option for an extension).
- **Info.plist**: the clip has no `UIBackgroundModes` (App Clips may not declare any): no silent pushes, the 60 s poll (see Push Notifications).
- **Entitlements**: Time Sensitive Notifications is only in the app's (unverified for App Clip App IDs; the clip's urgent alerts and reminders arrive as active). `applinks:` (app) vs `appclips:` (clip).
- **Asset catalogs**: each target has its own (`Attnd/Assets.xcassets`, `AttndAppClip/Assets.xcassets`), with the same accent colour and the same classic `AppIcon.appiconset` PNGs (see App icon).
- **Runtime only**: `SupportInfo` / `LogEnvironment` report "App Clip" (from the bundle id); the system may purge the clip's storage (saved bundle, plan, likes); App Clip limits Apple enforces (size, background execution) apply only to the clip.
- **Unverified on a device** (Nov 19, 2026): the `attnd-live` URL scheme in a clip (Live Activity taps), silent push wakes, scheduled Live Activity starts, MetricKit delivery and Foundation Models availability in an App Clip. The code paths are the app's and fail quietly (a tap just opens the clip; the 5-minute poll; the "tap to follow" notification; no reports; the search sheet without the model).
- **Size**: Apple's limit for clips opened from QR codes and NFC is 15 MB uncompressed (`-Osize` Release builds). Before the planner and assistant moved in the clip was 2.3 MB download / 4.8 MB install; it now carries nearly the whole app (the app's code was 4.0 MB with `-Osize`), so expect roughly the app's size (~5 MB install) plus the small widget extension. Dev builds are `-Onone` and much bigger (the unoptimised app was 24.7 MB install): watch the size report for the clip.

## Deep Linking (Universal Links)

They build their own client with `APIClient(serverHost:apiKey:apiVersion:attest:)` (static key, no App Attest) and are **skipped** unless the test process has `ATTND_IT_SERVER` (host) and `ATTND_IT_KEY`. xcodebuild forwards only `TEST_RUNNER_`-prefixed variables to tests (prefix stripped), so:
```bash
bash scripts/ci/test.sh build && ATTND_IT_SERVER=dev.attnd.app ATTND_IT_KEY=<dev key> bash scripts/ci/test.sh integration
# or: TEST_RUNNER_ATTND_IT_SERVER=… TEST_RUNNER_ATTND_IT_KEY=… xcodebuild test … -only-testing:AttndTests/APIClientIntegrationTests
```
In Xcode, put them in the scheme's Test environment locally (never commit a key). Device ids are `ci-ios-<run id>-<random>` and every test leaves the event. If the server's demo data changes, attnd-web's test of `load_demo_event` is the source of truth; update the three repos together.

## CI/CD (`.github/workflows/ios.yml`)

**Lean mode now (Nov 15, 2026, private repo minutes):** pushes to `develop` run only **Archive & upload**; the Test job runs on `main`, by hand (Run workflow) or with the repo variable `CI_FULL=true`, the integration suites only with `CI_FULL`. Batch commits and push when a change is ready to try on the phone; run the pure-logic tests in the Linux harness before pushing. Full pipeline below and how to restore it: attnd-web `docs/CI_PIPELINES.md`.

| Trigger | What happens |
|---------|--------------|
| Every run | **Test** (Mac, `xcode-27`): `scripts/ci/test.sh build` builds for testing once (`build-for-testing`, generic simulator destination, so it never waits for a device) while the newest iPhone simulator boots in the background; then three suites run with `test-without-building` on that build and simulator (`-parallel-testing-enabled NO`): **Unit tests**, **Integration · dev** (`ATTND_IT_SERVER=dev.attnd.app`, key `secrets.ATTND_API_KEY`; same-repo PRs only; non-blocking on `main`) and **Integration · prod** (`attnd.app`, key `secrets.ATTND_PROD_CI_KEY`, a CI key production accepts only for DEMO; pushes only; always `continue-on-error`, a failure is a warning). Each suite is its own step with its own warnings and pass/fail summary (`scripts/ci/test_summary.py` fails a suite whose tests were all skipped). |
| Push to `develop` | In parallel with Test: **Archive & upload** (Mac) archives the **Dev** configuration with the `dev` environment's `ATTND_SERVER`, exports it once locally to check that no bundle is signed with `get-task-allow` (the App Store export re-signs the development-signed archive with the distribution profile; TestFlight rejects debuggable builds), then uploads straight to TestFlight; nothing waits for processing (the only tester gets the build once Apple has processed it). The archive's dSYMs are kept as the artifact `dsyms-<build number>` (90 days, every archive) for symbolicating MetricKit reports. |
| Push to `main` | The same two jobs against `attnd.app` (archiving **Release**), then **Submit for App Review** (Linux, `needs: [test, archive]`, so a failing test blocks the release): store listing text (`asc.py metadata`) and the submission (`asc.py release`, which waits for processing), released after approval. What's New comes from `store/en-US/release_notes.txt` unless the `WHATS_NEW` repo variable is set. |
| Pull request | Test only (no archive). |

- **Compilation cache**: both Mac jobs build with Xcode's compilation cache (`COMPILATION_CACHE_ENABLE_CACHING=YES`, `COMPILATION_CACHE_CAS_PATH=build/CompilationCache`, set by `test.sh` / `archive_upload.sh` when `COMPILATION_CACHE_DIR` is set). `actions/cache` keeps it between runs per job (`ios-cas-test-…` / `ios-cas-archive-…`, keyed on the Xcode build version, so a new Xcode starts fresh); only pushes save it. The first run after an Xcode change is cold.
- **Timing (Nov 15, 2026, xcode-27 runner):** push → TestFlight upload ~8–9 min (was ~17½). The Test job is ~9 min, of which ~4–5 min is the fresh runner booting the simulator (xcodebuild waits for it before planning the build, then compiles in ~30–50 s); Archive & upload ~5 min in parallel; each test suite 30–50 s. Booting the simulator *after* the build was planned made the compile 6+ min (the boot takes most of the CPU), so `test.sh` starts the boot first. The compilation cache saves ~20 s per build (cold 50 s → warm 30 s). Moving the tested code into a simulator-free Swift package was considered and **rejected**: UI tests are planned and will need the simulator on every push anyway.
- **Size report** (`scripts/ci/size_report.py` + Apple's App Thinning Size Report from a thinned `release-testing` export, both informational, in the Archive step's log and summary): the `.ipa` per bundle (app, App Clip, the two widget extensions) and part (executable, Assets.car, other), and the per-device download (compressed) / install (uncompressed) sizes. Watch the App Clip: Apple's limit for clips opened from QR codes and links is 15 MB uncompressed. Measured Nov 19, 2026 with `-Osize` and tickets parked, before the clip got the planner, assistant, push and Live Activity: clip download 2.3–2.4 MB, install 4.8–4.9 MB (app code 4.0 MB; unoptimised 6.5 MB / 24.7 MB). The clip now compiles the same code as the app: re-measure.
- Docs-only commits (`*.md`) don't run; a newer push to `develop` cancels the older run (`main` never cancels). Anything that only waits on Apple runs on Linux (Mac minutes cost ~10×).
- Version = contents of `VERSION` + `.` + run number (e.g. `2.0.57`); build number = run number. Bump `VERSION` for a new major/minor line.
- **Signing** (`archive_upload.sh`): **manual** whenever `IOS_DIST_CERT_P12_BASE64` is set: the archive (`-xcconfig build/Signing.xcconfig`: `Apple Distribution`, `PROVISIONING_PROFILE_SPECIFIER = $(ATTND_PROFILE_$(TARGET_NAME))`) and the export (`signingStyle manual`, `provisioningProfiles` by bundle id) use the stored Apple Distribution certificate (`IOS_DIST_CERT_P12_BASE64`, `IOS_DIST_CERT_PASSWORD`, created Nov 19, 2026, valid one year) and four App Store profiles (`IOS_PROFILE_APP_B64` `com.arcu.Attnd`, `IOS_PROFILE_WIDGETS_B64` `.widgets`, `IOS_PROFILE_CLIP_B64` `.clip`, `IOS_PROFILE_CLIP_WIDGETS_B64` `.clip.widgets`; `ATTND_PROFILE_<target>` in the generated xcconfig). `scripts/ci/signing_profiles.py` installs them, prints their entitlements and expiry (warning < 30 days), and fails with the capability's name when an entitlements file asks for something a profile lacks (enable it on the App ID, regenerate the profile, update the secret). CI sets `aps-environment` to `production` in the app's and the clip's entitlements (the App Store profiles allow only that). No ad hoc profile, so Apple's thinning report is skipped (the `.ipa` breakdown stays). Without the distribution secrets it falls back to automatic signing via the API key. **Adding a capability** = enable it on the App ID, regenerate the profile(s), update the secret(s). Renewal: attnd-web `SETUP.md` (iOS signing). The upload always uses the App Store Connect API key (`ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8` secrets; the key needs the **Admin** role). The stored **Apple Development** certificate (`IOS_DEV_CERT_P12_BASE64`, `IOS_DEV_CERT_PASSWORD`) is still imported for the automatic fallback; renew yearly (attnd-web `SETUP.md` step 3e).
- Server host: `ATTND_SERVER` build setting → `Info.plist` → `APIClient.serverHost` (default `attnd.app`).
- Full setup checklist: `SETUP.md` in attnd-web.

## Store listing (`store-text.yml`, `store-screenshots.yml`)

App Store text and screenshots are generated and set on the **editable** App Store version (e.g. "1.1 Prepare for Submission"); nothing goes live until that version is submitted by `ios.yml` on `main`.

Two **manual-only** workflows (they never run with normal builds), plus the release:

| Workflow | What it does | Time |
|----------|--------------|------|
| `store-text.yml` ("Store listing text") | Validates `store/en-US` and (input **upload**, default on) runs `asc.py metadata` | ~1 min, Linux |
| `store-screenshots.yml` ("Store screenshots") | Mac: capture + compose → `store-screenshots` artifact; Linux: (input **upload**, default on) `asc.py screenshots` | ~20–30 min |
| `ios.yml` on `main` | Sets the listing text on the version (`asc.py metadata`), then submits it for App Review; screenshots stay as last uploaded | — |

- **When the user asks Claude to "update the store listing / screenshots"**: dispatch the workflow(s) on ref `main` (or `develop`) with the GitHub MCP `actions_run_trigger` (`run_workflow`, `workflow_id` `store-text.yml` / `store-screenshots.yml`, inputs `upload: true`), follow the run, download the `store-screenshots` artifact and show the user the images. Uploads only change the editable version (live after the next release). Manual runs need the workflow file on the default branch (`main`).
- **Text**: `store/en-US/*.txt` — `name`, `subtitle` (≤30), `promotional_text` (≤170), `description` (≤4000), `keywords` (≤100, comma-separated, no spaces after commas, not the app name), `release_notes` (sent as What's New, skipped for an app's first version), `support_url`, `marketing_url`, `privacy_url`, `review_notes` (App Review notes; no demo account), `captions.txt` (`<screen>=<caption>`, ≤2 lines, `|` forces the break). `python3 scripts/ci/asc.py metadata --dry-run` validates locally. Keep claims accurate to what the app does.
- **Screenshot mode** (`ScreenshotMode` in `Helpers.swift`; launch arguments only, never persisted): `-AttndScreenshotMode YES -AttndScreen <map|map-pane|locations|location|schedule|updates|orientation-probe>` joins event `DEMO` through the normal lookup/join path, skips the launch screen, update check, device registration, usage counts, demo badge, blue dot and push, forces fit-all/no clustering/now-next, opens the screen (`location` = "Main Stage" detail; `map-pane` = map + side pane) and writes `Documents/attnd-screenshot-ready` (`ready <screen> <W>x<H>` window points, or `failed <reason>`). Needs a simulator Debug build with `ATTND_API_KEY` + `ATTND_SERVER` = the dev server (the static key only works there).
- **`scripts/ci/screenshots.sh`** (macOS): builds once; picks the newest `iPhone NN Pro Max` (6.9", 1320×2868), `iPhone NN Pro` (6.3", 1206×2622) and `iPhone Duo` from `simctl list … -j`, creates/boots them, light mode, 9:41 status bar, captures each screen into `build/screenshots/raw/<device>/<n>-<screen>.png`. The iPhone Duo is captured **folded** (cover display → `raw/iphone-duo-cover/`: map, schedule, location, updates; window < 600 pt wide) and **unfolded** (inner display → `raw/iphone-duo/` in portrait, or `raw/iphone-duo-wide/` 2853×2007 when the simulator keeps the inner display in landscape, which it did on Xcode 27.2 in Nov 2026: map-pane, location, schedule, updates). It boots folded and Xcode has no public hinge control: `scripts/ci/duo_hinge.m` (private SPI, run inside the simulator with `simctl spawn`) unfolds it; the app's reported window size confirms the inner display (≥600 pt wide, portrait), captures use `--display=<active display>` (devicectl), and an orientation probe lets the composer rotate sideways captures. If folding or unfolding fails, that Duo set is skipped with a warning (repo variable `DUO_SCREENSHOTS_REQUIRED=true` makes it fatal).
- **`scripts/ci/compose_screenshots.py`** (Pillow): purple gradient `#431F86 → #7B4FD6`, bold white caption (SF from the macOS runner, fallbacks), rounded/shadowed capture; outputs exactly 1320×2868, 1206×2622, 2007×2853 (Duo unfolded) and 1398×2034 (Duo folded) RGB PNG in `build/screenshots/composed/`.
- **`asc.py metadata`** / **`asc.py screenshots`**: version localization, app info localization (name, subtitle, privacy URL), App Review details; screenshot sets `APP_IPHONE_67` (6.9"), `APP_IPHONE_61` (Dynamic Island medium display, 1206×2622) and `APP_IPHONE_DUO` (unfolded screenshots first, then folded, ≤10 in total; accepted by the live API, not yet in Apple's reference; if it is ever rejected, the accepted values are printed and the run continues). Existing screenshots in those sets are replaced.
- **Repo variables** (optional): `REVIEW_CONTACT_FIRST_NAME`, `REVIEW_CONTACT_LAST_NAME`, `REVIEW_CONTACT_PHONE`, `REVIEW_CONTACT_EMAIL` (App Review contact; left unchanged when unset), `SCREENSHOT_SERVER` (default the dev server), `DUO_SCREENSHOTS_REQUIRED`. Secrets: `ATTND_API_KEY` (repo) and the environments' `ASC_*`.
